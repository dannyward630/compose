### 7. Escalate and clean
A task that exhausts its attempts comes back with its full log. Read the log, then split: write two or three smaller, more specific tasks that each name the exact function, file, and behavior the log shows the implementer missed, have the test-writing teammates give each its own red test, and dispatch those. Never re-dispatch the same task unchanged, and do not pick up the keyboard yourself just because an attempt failed. The exhausted task's issue is Canceled with a comment pointing at the issues that replace it; the new tasks get their own issues, blocked by whatever the old one was blocked by.
The re-split is a change of course: sync, then `compose change start --why "<one line>"` before you edit Linear, and sync, then `compose change done` after (step 8).
When the blocker is not the task (the fast provider is down, or the task cannot be made smaller than one function), the work still goes to a teammate, never to your keyboard: set `model: claude` in the task's block and `run --only` it, or brief a teammate session for it. Work teammates did outside `run` is recorded with `compose done --project <name> --only 024,025 --note "provider out of credit; done by <slug>-<role>"`, so `compose status` shows the truth, and the report says so. That includes a teammate's commit on top of a passed layer: the layer stays in the stack, and a later `run` keeps a hand-done branch exactly as it keeps a passed one, unless `--redo`.
A rebase conflict while stacking (`after: ... could not be chained`) is teammate work too: brief one with the two branches and the conflicting files.
The run goes on without that task: it is `unchained`, the tasks after it are blocked by it, and `run` or `resume` starts it once the chain rebases.
`compose status --repo <path> [--watch]` shows every project with each task's state, attempts (the ones spent: a rate-limit or busy-provider wait costs none), time, cost, and stack layer; use it to report progress instead of describing it from memory. `compose watch` is how you wait for it to change.
`compose clean --project <slug>` is the post-merge step (never repo-wide: that touches every project), run after the reviewer has merged PRs on GitHub (or the user merged locally): it fetches, removes task clones and the CLI's stack worktree, deletes task and layer branches that are proven merged, and once every layer and the project branch are merged it removes the project's worktree and branch too.
It moves Linear first, and never removes a worktree someone still stands in: run from inside the project worktree, or while the team lead has not reported done, it keeps the worktree and project branch and says why.
The team lead's `done` then removes them once its turn ends (inside herdr), or it names the `compose clean` to run from outside; `--project <slug> --force` removes them under a team lead, never under the command itself.
`compose clean --abandon --project <slug>` drops an unmerged project the product owner gave up on, and only with that flag: it lists what it removes (worktree, local branches, herdr tabs, results) and what stays (Linear, branches pushed to a remote), then removes them; `--dry-run` only lists, live crew needs `--force`. Cancel its Linear issues yourself.
A branch counts as merged into a target when it is contained in the target, when every commit on it has its patch in the target (`git cherry`), or when merging it into the target would change nothing (`git merge-tree --write-tree` gives the target's own tree without a conflict, which covers a stack re-cut onto a moved base), and last when a merged PR on GitHub names it (which also covers squash and rebase merges).
Any doubt means not merged.
Task and layer branches are checked against the layers' review base (`review_base` in verify.json) and its remote first, then the trunk, its remote, main, and master.
Unmerged work is kept and named: a kept branch, the project branch included, gets one line, `clean  <branch>: kept unmerged, first unmatched commit <short sha> <subject>`, with ` and <n> more` when there are more.
It never deletes unmerged layers unless `--delete-unmerged`. Run it whenever the user says PRs were merged, and at the end of a feature. It also keeps Linear true (0s) with the workspace's key: every task it proved merged moves to Done, its story rolls up, and the feature is Done once every story is and the project branch is merged; a Canceled task stays Canceled. You move none of these yourself; the epic rolls up from the feature as 0s says. Without a key it prints one `linear skipped` line, and the states are yours until the key is set. A task you did by hand (`compose done`) is proven merged the same way and goes to Done with the rest.
