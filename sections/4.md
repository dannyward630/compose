### 4. Dispatch
`compose run --repo <path> --project <name>` runs tasks in dependency order: independent tasks in parallel, one clone and one implementer session (pi by default) each; a task with `after:` starts as soon as that task passes, on top of its branch. The implementer edits and ends its turn without running anything; the CLI then runs the task's test itself. Test failures, an over-limit diff, a new document, or a change outside `files:` are fed back into the same session up to `--attempts` (default 3); a test failure goes back with the test reader's short fix brief (`models.test_reader`, Claude Haiku in Claude Code with read-only tools: which cases fail, expected versus got, the file:line to look at) ahead of the raw tail and the full log's path, and with the raw tail alone when the reader fails or times out. The reader's cost is on the attempt's line (`reader $...`) and in the task's cost. It runs on the Claude Code subscription, never an API key or OpenRouter: every headless Claude call the CLI makes drops `ANTHROPIC_*` from its environment, so that figure is Claude Code's reference cost, not a bill.
Each clone, and the worktree verify runs in, borrows the main checkout's git-ignored installs (`node_modules` at any depth, `vendor`, `.venv`) as symlinks that never show in `git status`, and trail never edits `.gitignore` there. So install dependencies once in the project worktree before `run`; do not patch test commands to link them.
A repo with a commit convention (type prefixes like `feat:`) declares it once as `commit_convention` in verify.json, `{"types": ["feat", "fix", "chore", "test", "docs", "refactor", "build", "ci"], "example": "feat: add resume upload"}`; every commit the CLI makes and every teammate brief then follows it, and an undeclared one keeps plain messages.
When the build output must match the project worktree byte for byte (a bundler that writes dependency paths into unminified output does not), set `install` in verify.json (for example `bun install --frozen-lockfile`): it runs in each clone and in verify's worktree instead of borrowing, so no checkout shares the project worktree's `node_modules`. Unset keeps borrowing.
A task whose `files:` names a lockfile borrows nothing: it installs fresh in its own clone, and when it passes that install replaces the project worktree's, so later tasks and verify see the new dependencies.
The trunk is the branch the user is on when you run it (`--trunk` overrides). That checkout is never switched: clones are separate repos, and every `gh stack` operation runs in a CLI-owned detached worktree under `.compose/<project>/worktrees/.stackroot`; gh stack keeps its state in the repository's shared `.git`, so `gh stack view` works from a task branch there too.
When the run ends, all passed task branches of the project are rebased into one linear chain on the trunk tip, and the chain is cut into review layers registered as one gh stack on the real base (`review_base` in verify.json, else the default branch): `(main) <- <project branch>-layer-01 <- <project branch>-layer-02 <- ...`, printed on a `stack ok` line, with one `layer NN` line each.
Task, test-writer, and layer branches are named `<project branch>-NNN`, `<project branch>-tests-NNN`, and `<project branch>-layer-NN` for every project, but a project whose `fast/<project>/` branches already exist keeps those names, recorded as `task_prefix` and `layer_prefix` in verify.json until `clean` removes the branches.
Tasks stay tiny for implementers; the layers are sized for the reviewer.
Consecutive tasks, in stack order, are grouped into one layer up to `review_layer_lines` in verify.json (default 300 changed lines), and a task is never split, so a task over the budget is a layer of its own.
A stack opens at most `max_stack_prs` PRs (`~/.compose/config.json`, default 10, `verify.json` overrides), and past it adjacent layers fold into one, same kind first.
Lockfiles (`package-lock.json`, `bun.lock`, `yarn.lock`, `pnpm-lock.yaml`, `go.sum`, any `*.lock`) are not counted, in a layer or in a task's 350 lines; each `layer` line names them and their size, and the same line becomes the size line under the PR body's `## What changed`.
The project branch is not a PR: its groundwork commits (scripts, CI, baseline, stubs) become layers of their own, at most the same budget each and never mixed into a task's layer, below the first task layer, and each task's acceptance tests move into its task layer.
Layers are rebuilt from the commits on every stack, with the original committer and date, so unchanged layers keep their hashes and a resubmit pushes nothing new.
If the layers would not add up to the task chain's tree, or a commit does not apply in layer order, the CLI says `stack  STOP` and stacks the task branches as they are; read that line before pushing. A later wave grows the same stack; before it starts, the existing layers are rebased onto the current trunk so new tests and task files are present on every base. A rebase conflict stops the chain at that layer with the exact commands to resolve it. `--no-stack` skips that rebase before dispatch and the registration; a task with `after:` still rebases the layers it stacks on.
Use `--only 003,004` for a subset.
Run it in the background (`run_in_background`). `run`, `verify`, and `resume` work in their own session and log to `results/<command>.log`, which the background task streams; a closed tab or a crashed session ends only that stream, never the work, and `watch` still reports how it ends. Your job during a run is supervising the teammates and keeping Linear true, not typing code, and not polling. Supervision costs zero tokens while nothing happens:
- Inside herdr you do not start `watch`: your tab's Stop hook (`compose rewake`) parks one each time your turn ends, and its event wakes you as Stop hook feedback. Act on it and end your turn; the hook parks the next one.
- Outside herdr, start `compose watch --repo <wt> --project <slug>` in the background too. It sleeps until something you must act on happens, prints one `event ...` line, and exits; its exit wakes you. Act on the line, then start `watch` again. Run exactly one `watch` per wake-up, never a loop of several (`for i in 1 2 3; do compose watch; done` waited 8 minutes on events that had already arrived). `watch` gives up after 10 minutes with a `timeout` line summarizing what is pending, so you are never parked forever. Never loop on `status` or `herdr agent list` yourself.
- The event lines, and what you do with each: `task=NNN state=running` and `state=passed` need nothing from you on Linear (the CLI moved the issue and rolled its parents up); `state=failed` or `state=rejected_*` goes to step 7; `state=contradiction` and `event reflect=...` go to step 8; `agent=<name> status=blocked` means read it and steer; `run=ended` means review the stack; `verify=PASS|FAIL` means report (on PASS the CLI moved the feature to In Review). A status line is a wake event, not current state: before a decision, confirm with `compose status` and the result file.
- `crew=<name> skill=stale changed=<files>`: a pi teammate (pi runs no Claude hooks) is working from skill files that changed since it started; relay it with `herdr agent prompt <name> "compose's skill changed since you read it: <files>. Re-read the ones your role uses before acting."`.
- Read before you act: `herdr agent read <slug>-NNN --source recent-unwrapped --lines 80`.
- Steer with one specific instruction: `herdr agent prompt <slug>-NNN "<what to change, which file, which test>"`. The CLI's own re-prompts and yours go to the same agent, so keep yours short and concrete, and never contradict the task issue; if the task is wrong, fix the task and re-run it.
- A stalled agent (working, no output change for a few minutes) gets one nudge, then `compose` times it out into a fresh session by itself; do not kill panes.
- Log each steer as a comment on the task's Linear issue, one line, so the trail is in the ticket and not only in a terminal.
The CLI keeps Linear's state table true on the full path, with the active workspace's Linear key: a dispatched task moves to In Progress, a passed one to In Review with a comment naming its branch, attempts, cost, and model, a failed one stays In Progress with the failure as a comment, and its story and the feature roll up after each change (0s); the run's end and verify PASS roll every story up again from its tasks, so a roll-up one event missed is made true, and verify PASS moves the feature to In Review once every story is. You never move these states or write these comments yourself: you create and edit issues, and write the judgment comments (reviews, decisions, why a task was re-split). Without a key the CLI prints one `linear skipped` line; tell the product owner to run `! pbpaste | compose workspace key <workspace> --linear`, and until then move the states yourself as the table says. Done comes with the merges: `compose clean` moves it (step 7).
Nothing is pushed.
`compose stack --submit` runs `gh stack submit --auto` on the layers, which pushes every branch, opens one draft PR per layer, and links them as a GitHub stack; it then checks each layer has its PR on the layer below (`submit PR #N on <base>`, or `NO PR for <branch>`).
It titles each PR from its commits: one commit's subject, else the first task's title or the first groundwork subject plus `and N more`, with the Jira key and `(i/n)` kept.
It writes a body with `## Why`, `## What changed`, `## How it was tested`, and `## Tickets`, built from the task issues and results with no model call.
Without `--submit`, `compose stack` prints each layer's title and body as a `pr` line, with no `gh pr` call, so you can read them before you ask for the push.
Run it only when the user has explicitly asked for that push.
