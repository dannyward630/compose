### 6. Verify
`compose verify --repo <path> --project <name>` is the local no-mistakes-style pipeline. Nothing is pushed; the only network calls are model APIs. Stages, in order, from `.compose/<project>/verify.json`:

```json
{
  "checks": ["uv run ruff check .", "node --test 'tests/**/*.test.js'"],
  "docs": ["README.md", "DESIGN.md"],
  "perspectives": ["correctness", "security", "spec", "docs"],
  "jev_acceptance": true, "acceptance_threshold": 0.6, "acceptance_gate": false,
  "e2e_setup": "cd ... && python -m server.server", "e2e_setup_wait": 3, "e2e_env": {"API_KEY": "..."},
  "e2e": [{"name": "greenhouse fill", "url": "https://...", "goal": "Fill the application ... stop before Submit.",
           "assert": "python scripts/check_greenhouse.py", "prices": {"typesafe_per_call": 0.0}}],
  "review": true, "review_base": "main", "fix_model": "pi:openrouter-fast/z-ai/glm-5.3-flash@preset/glm-5-3-flash-fast",
  "review_context": "Design facts reviewers must respect, e.g. test credentials come from env by design and never reach the server."
}
```
e2e runs at the same time as review and jev acceptance, right after checks, since those two only wait on model calls.
Each e2e stage gets two fresh free ports, `$E2E_PORT` and `$E2E_CLIENT_PORT`, in the environment of `e2e_setup`, `setup`, `driver` and `assert`, and expanded in every value of a case (`url`, `goal`, its `env`) and in `e2e_env`.
Use them; never hardcode a port, unless the app itself pins one (then keep that one and nothing else fixed).
Start servers in `e2e_setup` with a plain `&`; never free ports there with `lsof | kill`.
The cases start once every port `e2e_setup` names accepts a connection (up to 60 s, or `e2e_setup_wait` if longer); a setup that names neither port, like an extension's browser on a pinned port, waits a fixed `e2e_setup_wait`. A case's own `setup` and `setup_wait` work the same way.
A case's `setup`, jev case or driver case, starts before that case and ends after its `assert`, for example to log in a different user for that case.
e2e driver and assert scripts live in the project, under `.compose/<slug>/e2e/`, referenced by that path in `verify.json`; verify's worktree links the project's `.compose`, so they resolve there. Never put them in `~/.compose`, `/tmp`, or anywhere outside the project, where teardown and `clean` cannot find them.
Each e2e stage also launches its own `bp` Chromium on a third fresh port with a throwaway profile, and sets `BU_CDP_URL` and `BU_NAME` for `driver`, `assert` and jev, so verify never attaches to the user's real Chrome and no project launches a browser in `e2e_setup` for that.
The stage's browser is headless, since an unattended verify runs while the display sleeps and a headed Chromium then stops painting.
`"e2e_headed": true` shows it to watch a run; on macOS the stage then keeps the display awake with `caffeinate` while it lasts.
A stage whose `e2e_env` sets `BU_CDP_URL` itself (an extension's Chromium, see 6a) uses that browser.
A project whose cases need no browser at all (`driver` cases for a terminal app) sets `"e2e_browser": false`: the stage then starts none and sets no `BU_CDP_URL`.
The stage ends everything it started when it ends, pass or fail: the setup's process group, its own browser and that browser's harness daemon, and anything left listening on its ports or the browser's CDP port, so no server or browser outlives a round.
A SIGTERM or SIGHUP to verify ends them too, and the next stage ends the browser of a verify that was killed outright.
A failure that is the harness's (a jev or browser crash, a missing tool, a port in use) is reported as `TOOL ERROR`, retried once, and never handed to a fix round; only app failures are.
1. **checks**: lint, unit tests, and the 0g smoke checks, exact and cheap, run first. Formatting is already done: `run` formats each passed task's own files (gofmt, the repo's installed prettier) before committing, and keeps the unformatted version if formatting would break the test.
   Only the first round runs every check up front.
   A fix round runs the `test:` commands of the tasks whose files its fix changed (`check  scope` line), then the full checks once, only after every other stage passed (`check  full` line).
   A fix that changes a file no task names runs the full checks instead.
2. **review**: parallel fast-model reviews (Mercury 2.5, keys in `~/.compose/.env`), one per perspective, then a confirmation call per high or medium finding that must quote the wrong line and say how it must read (a line that must read as it already does is no defect). Unconfirmed findings are dropped and shown as dropped. Only confirmed highs fail the stage.
3. **jev acceptance**: every bullet under `## Acceptance criteria` in every task issue becomes one choice question to Jev (TypeSafe): MET, NOT_MET, UNCLEAR, with probabilities, one request per task against that task's own files, then a confirmation call per NOT_MET. Advisory by default, since the tests already cover every criterion; set `acceptance_gate: true` to make confirmed NOT_MET fail the stage.
4. **e2e**: each case drives the stage's own browser with jev (`jev/`) to the goal, then runs `assert`, an independent check (written by the test-writing teammates) that reads the real DOM or run log. A DONE from the model is never the proof.
   The `assert` runs after every jev run, also one that gave up or crashed, so an assert that resets the app for the next case always runs.
   A form login needs a password jev never sends to a model: give the case `"secrets": {"Password": "$E2E_PASSWORD"}`, keyed by the field's label, with the value in the environment (`e2e_env`, `~/.compose/.env`); jev types it itself.
   Without one, jev skips the password field and its stop reason says so.
   A jev run that does not reach its goal shows its stop reason on the `e2e` line, the page it stopped on, and its last steps; `results/verify.json` keeps every step, and `results/e2e/<n>-<case>/` its step screenshots.
5. **fix loop** (`--fix N`, default 2): confirmed findings go to the fast implementer in the repo itself, protected files are reverted if touched, the files the fixer changed are committed (never the agent wiring a session hook rewrites, nor a check's leftovers; your own uncommitted changes skip the fix), and every stage runs again, with checks scoped to the fix as in 1. A fixer has the tasks' scope: a round that touches any file the stack does not already change and no task names in `files:` (a lockfile, `setupTests.js`, a new `package-lock.json`) is reverted whole and verify ends FAIL. Treat that FAIL as an environment problem for a teammate, not a finding. After N rounds it escalates to you with the findings. `--fix 0` reports only.

Every line prints its clock time and duration. The last line is the cost ledger: dollars and tokens per provider (openrouter for implementers, fixes, Mercury reviews, and jev's text helper; cerebras when a task pins it; typesafe for Jev decisions) and the total. `+?` after a provider means tokens were counted but no price is configured; set `prices` in verify.json to price it.

Fix what fails, re-run. Only then tell the user it is done, with the verify output.
Then write each layer's PR text and show the `compose stack` preview with it (step 4).
