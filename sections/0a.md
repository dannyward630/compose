### 0a. Put the work in a project, in its own worktree
A project is one feature: its own git worktree and branch, one plan, one set of tasks, one gh stack. The moment the user invokes you with a task, decide which project it belongs to before anything else:
- Run `compose projects --repo <path>`. If the request continues a feature that already has a project (same spec, same area of the code, or the user names it), use that project: new tasks get the next ids and become new layers of its stack.
- Otherwise create one: `compose init --repo <path> --project <slug>`, where `<slug>` is a short kebab-case name for the feature in the user's words (`custom-dropdowns`, `workday-login`), not the repo's name and not a date. This creates branch `compose/<slug>` (or the name given with `--branch <name>`, stored as `branch` in `verify.json`; use it when the repo's convention wants a ticket key in the branch name) from the branch the user is on and checks it out in a treehouse slot from the repo's own pool (`<repo>/.treehouse/`, git-ignored), with `.compose/<slug>/` there, untracked. Worktrees for test-writing teammates, stacks, and the toolsmith are leased from the same pool and returned when their work is done, so the next agent gets a slot with its installs intact; the work always lives on branches, never in a slot. Without treehouse installed, `init` prints its install command and uses plain git worktrees (`../compose-<slug>`) instead. Task clones for implementers stay plain `git clone --shared` copies.
Before anything else it ignores the tool's files: `graft/`, `.trail/` (where trail keeps the graph), and `.compose/` go into an existing `.gitignore` as one commit of its own (`Ignore local tool directories`), and into the repo's `info/exclude` whether or not a `.gitignore` exists, so no tool file ever enters the branch.
Projects created before this keep their already-tracked `.compose/<slug>/`; nothing about them changes.
In a repo that already has code, `init` then sets trail up in the worktree: wired for Claude Code (`trail init --no-agents --no-global`, skipped if it would edit a tracked file) and built, with every file trail writes kept out of git through `info/exclude`. Without trail installed it prints the install command; `compose trail --project <slug>` sets it up later or rebuilds the graph.
Tell the user the project name and the worktree path in your first reply.
- Inside herdr, right after `init` and the feature issue exist, hand the project to its team lead (0h) and become the engineering manager. The rest of this skill is the team lead's.
- Every project is one **feature issue** on Linear (label `Feature`, title in the user's words, under its epic when there is one). Create it if the user did not hand you one, and record its identifier in `.compose/<slug>/linear.json` as `{"feature": "ENG-123"}`. Its stories, their tasks, and any decision tickets are its sub-issues, so the whole feature reads as one tree in Linear.
- Set `"stories": ["ENG-124"]` in `linear.json` when two projects share one feature, or when a project picks up a later story after an earlier one merged: sync, tasks, run, and stall checks then see only those stories and their tasks.
  A task Done on Linear is never pending or run, scoped or not; with no `stories`, every task under the feature syncs as before.
- From then on everything you do in code for this project happens in that worktree: acceptance tests, every commit, every `compose` command (`--repo <worktree>`, or any checkout with `--project <slug>`: the CLI resolves it). Everything written in words (grilling notes, the plan, tasks, decisions) goes to Linear, never to a file (Rules). The user's own checkout and branch are never touched. Several projects can run at the same time, each in its own worktree with its own stack.
- The stack's trunk is the project's branch (`compose/<slug>` unless `--branch` chose another); `compose init --project <slug> --branch <new>` on an existing project renames its git branch and stores it.
  Its review layers sit on the review base (`review_base` in `verify.json`: `init` records the branch the project started from, and one that names no branch reads as the repo's default branch), and `gh stack merge` lands the whole stack as one all-or-nothing merge.
  No PR takes the project branch anywhere.
- A project made with `init --after <other-slug>` starts from that project's stored branch, records it as `review_base` in its `verify.json`, and shows `(after <other-slug>)` in `projects` and `status`.
  Its layers stack on that project's branch, which itself lands on the user's branch.
  `clean` counts a merge into either.
  On a project that exists already, `init --after <other-slug>` moves it onto that branch while it has no commits of its own and a clean worktree (agent wiring a session hook rewrote, like `.claude/settings.json`, aside), and otherwise stops with the reason.
  `sync` links the project's feature issue blocked by that project's feature issue.
  Link a feature blocked by another only when it needs that feature's code: it calls, imports, or edits what that feature builds.
- Never mix two features in one project, and never spread one feature over two. If a request is really two features, make two projects and say so.
`compose status --repo <path>` shows every project in every worktree with all its tasks; `--project <name>` shows one. Use these when reporting progress.
