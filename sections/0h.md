### 0h. Inside herdr, the fleet is visible and steerable
You are inside herdr when `HERDR_ENV=1` (herdr also sets `HERDR_SOCKET_PATH`, `HERDR_PANE_ID`, `HERDR_WORKSPACE_ID`). Then read ~/.claude/skills/herdr/SKILL.md; it carries the safety rules for panes and agents.
`herdr agent get $HERDR_PANE_ID` tells which harness you are (`claude` under Claude Code, which also sets `CLAUDECODE=1`; `pi`; ...). The flow is the same for any team lead; only the harness-specific tools differ.
The CLI builds the topology by itself, named so the product owner reads it at a glance:
- **space** `<slug>`: the project's worktree, opened as a herdr worktree space grouped under the space open on the repo (the one `init` was started from, or any of the repo's); no other space is opened. When no space of the repo is open (compose started from another repo's space), the project's tabs go in the space `init` was started from instead, recorded in `results/herdr.json` so every later command finds it, each labelled `<slug> <name>` there (`<slug> status`, `<slug> orchestrator`) so projects sharing a space never touch each other's tabs
- tab **`status`**: `compose status --watch` running live; tab **`shell`**: a shell in the project worktree; every tab's cwd is the project worktree, and a tab of one pane (`status`, `shell`, each teammate's) names its pane like the tab
- the pane compose was started in, labeled **`manager: <slug>`** by `init` and `crew start` (every project it runs, comma-separated, each taken off again by its `clean`); a label the product owner gave that pane is kept
- tab **`implementers`**: one pane per running task, labeled **`NNN <title>`**, holding the task's interactive pi agent named **`<slug>-NNN`**, with state labels (`attempt 2/3`, `rejected_size`) and tokens (`model`, `cost`) on its pane. A passed task's pane closes; a missed one stays to read and steer
- tab **`verify`**, rebuilt by each verify run: one pane per stage (`checks`, `e2e <name>`, `review`, `jev`), reported `working`, then `idle` ok or `blocked` FAIL
`<slug>` is the project's (0a); until a project exists it is a kebab-case name for the map in the user's words.
An agent name written `<slug>-<role>` or `<slug>-NNN` here is the one herdr registers, and herdr names stop at 32 characters, so a longer one keeps its role and cuts the slug: project `clean-recut-branches` has team lead `clean-recut-branche-orchestrator`.
In every `herdr agent` command use the name `crew start` printed and `compose crew list` shows; `watch --from` takes the role.
**Three roles, adapted from firstmate** (github.com/kunchenguid/firstmate). The product owner is the user.
- **Engineering manager**: the session the product owner started. It stays in the pane it was started in and is the product owner's one point of contact. It takes the intake (0, 0j) and creates the project (0a), then hands the project to a team lead and only relays from then on. It never moves, and one engineering manager can run several projects.
- **An epic as a unit** (0j, settled path): the engineering manager creates every feature's project and team lead, runs one `watch` per project, and relays as above. It reports at epic level: features verified X of N, total cost and wall time, and which feature waits on what. It keeps the epic's Linear state in step with its features (0s). It still writes no code and does no team lead's work.
- **Team lead** (role, tab, and `models.crew` entry `orchestrator`; agent `<slug>-orchestrator`): a Claude session in the project's space, started by the engineering manager right after `init`: `compose crew start --repo <wt> --project <slug> --role orchestrator --title orchestrator --brief -` with a brief on stdin naming the project, the worktree, the feature issue, what the product owner asked, and "read SKILL.md, sections/0h.md, sections/0a.md, sections/0e.md, sections/0g.md, sections/4.md, sections/5.md, sections/6.md, sections/6a.md, sections/7.md, sections/8.md and \~/.claude/skills/herdr/SKILL.md, then continue from 0b". It runs everything from there on. It reports up with `compose report`, and the product owner can also type into its pane directly.
- **Teammates**: sessions the team lead starts in the same space: the wayfinder teammate (0b), the planner teammate (`compose planner --project <slug> --issue <id> --extra - | compose crew start --project <slug> --role planner --title planner --brief -`, or `/compose:planner <ticket>` from the engineering manager; it continues specing at step 1, 2, or 8, runs on its own `planner` model entry, writes Linear under the same guard as the team lead, and never dispatches), helpers (researchers, writers, reviewers), the implementers `run` starts, and for design work the designer with its `design-NNN` builders and its `design-review` reviewer (0d).
The CLI directs the product owner's attention, not you: every `needs-user` or `blocked` report badges that pane `needs you`, and the one desktop notification pops when such a report wakes the engineering manager's `watch` (the session with no crew role), so the product owner is alerted only for what reaches the engineering manager, never by a teammate or the team lead directly. The CLI sends that notification itself (macOS `osascript`, elsewhere `notify-send`), never through `herdr notification show`: herdr's own toast and sound fire for every agent that finishes or needs input, so herdr's `[ui.toast] delivery` must be `"off"` and `[ui.sound] enabled` must be `false` in `~/.config/herdr/config.toml` (`compose doctor` warns when they are not), and those settings leave the CLI's notification untouched. Nothing steals focus. When the product owner says "take me there", run `compose crew focus --project <slug> --role <role>`.
The engineering manager's loop: `compose watch --repo <wt> --project <slug> --from orchestrator` in the background; on each `event crew=<slug>-orchestrator` line, tell the product owner the outcome in one or two sentences (needs-user: the question and its recommendation, and that the product owner may answer here or in the team lead's tab); forward the product owner's answer with `herdr agent prompt <slug>-orchestrator "<answer>"`; start `watch` again.
That one watch also reports every teammate the engineering manager started itself, a planner or designer from `/compose:planner` or `/compose:designer` with no team lead to go through: `crew start` records who a teammate reports to (`reports_to` in `results/crew/<agent>.json`: the engineering manager when the starting session has no `COMPOSE_ROLE`, else that role), and the engineering manager's watch passes their events whatever `--from` says, so their `needs-user` and `blocked` alert the product owner the same way. Never start a second watch for such a teammate: it waits on the first one's lock, and the teammate's reports wait with it.
`crew start` also records which session started a teammate (`started_by`, the herdr pane it runs in), so two engineering manager sessions on one project never mix: each session's watch has its own memory and lock, and wakes on no line of a teammate another live session started (nor of that session's team lead and its teammates) unless `--from` names it.
A teammate whose starting session has ended is adopted by any engineering manager's watch.
A `needs-user "<issue>: <n> cards <ids>; recommendation <one line>"` from the wayfinder or the planner is forwarded by the team lead unchanged and never re-sent in full; the engineering manager reads the issue once and asks the product owner every card in full, and the answers travel by card id: `herdr agent prompt <slug>-wayfinder "<card id>: <answer>, ..."`.
Read the team lead with `herdr agent read <slug>-orchestrator --source recent-unwrapped --lines 80` before relaying anything unclear. Do not do the team lead's work yourself.
The engineering manager's own session is outside the CLI's reach: it runs unrestricted, with every server and skill the product owner has.
Compose itself uses no Linear MCP, and this session uses `compose linear` too, never a Linear MCP.
A Linear MCP write returns the whole issue into this session's context, while a `compose linear` write prints one line, and `create` and `update` take `--priority`.
The engineering manager supervises, it does not only relay. `watch --from orchestrator` also wakes it on `event stall=...`: work is pending and nothing has moved for the stall window (`quiet`), every test-writing teammate is done and nothing is dispatched (`undispatched`), a run or verify ended with no team lead report since (`no-next-step`), or the team lead has sat idle with tasks pending (`idle`).
On a stall, read the team lead's pane, find what it is waiting on, and nudge it: `herdr agent prompt <slug>-orchestrator "<what you saw and the next step>"`, or `herdr agent send-keys <slug>-orchestrator esc` first to interrupt a stuck command.
Each stall fires once; escalate to the product owner only if the next stall window passes with no progress after your nudge.
The window is 240 seconds by default; set `stall_seconds` in the project's `verify.json`, or pass `watch --stall <seconds>`.
On `event ready=<ids>` it tells the product owner unprompted, in one line, `can start now: NEB-x <title>, ...`, and the event raises no desktop notification.

**Yolo: the product owner is away** (`/compose:yolo [--push] [words]`, `compose yolo`; modeled on firstmate's away mode).
It is a posture stored in `results/yolo.json`: it changes who answers a decision and how the product owner hears of it, and never widens what is allowed.
It is per project, so it covers every engineering manager session on the project: `watch --now` (`by=`) and `status` say which session set it, and a question line under yolo another session set names that session.
While the file exists, the engineering manager answers the team lead's `needs-user` itself with the recommendation, sent exactly as a product owner answer would travel (`herdr agent prompt <slug>-orchestrator "<answer>"`), and no notification pops.
Wayfinder or planner cards are answered `yolo: <card ids>: accept-all`, the `yolo:` prefix making the wayfinder record each line `(yolo recommendation, unconfirmed, <date>)` and never as the product owner's; a 3b departure gets "go", and a change of course (step 8's "goes back to the product owner" included) gets the recommendation.
Log each answer at once: `compose yolo decided --project <slug> "<question>: <answer taken>"`, which prints the `yolo:` form to send.
A planner cutting on an unconfirmed line says so on the story or task.
Write each `compose yolo` command out in full, never from a shell variable: zsh passes an unquoted variable as one word, and yolo refuses words that look like a command; `compose yolo --project <slug> --clear-words` empties words stored by mistake.
The words in the file pre-answer a question verbatim, never by analogy; a doubt the words leave open is held for the return, and the rest keeps running.
When the team lead reports done: with `push: yes`, tell it to run `compose stack --submit`; with `push: no`, the stack waits.
The never-set still stops and lands in "Waiting on you": destructive, irreversible, and security-sensitive actions are never pre-authorizable whatever the words say.
That covers anything that costs money beyond the configured models (a model or provider switch, keys), the payment halt, merging a toolsmith fix into compose itself, force-push, `clean --delete-unmerged`, `crew stop --force`, attended prompts (Frame0 Allow, sign-ins), and anything the product owner's CLAUDE.md forbids.
The product owner's first ordinary message is the return: run `compose yolo off --project <slug>` (every project of an epic), relay the digest, and ask its "To confirm" decisions in one ask (accept all, or name the ones to change) before work built on them goes further, then act on the message.
Bias toward exit: when unsure whether a message is the return, it is.

**A change of course reaches the product owner through you.**
Relay the team lead's `needs-user "change <id> on <slug>: ..."` line as it is: what was found, what is held, that the rest keeps running, the page, and the recommendation. For the one-line card report above, the forwarding is already said there; point back to it in a few words, not again in full.
When the product owner says the plan changed, forward their words: `herdr agent prompt <slug>-orchestrator "change of plans: <their words>"`; the team lead screens them and holds what they touch (step 8).
When the line in question is the epic's, not one feature's, tell every team lead under that epic: `herdr agent prompt <slug>-orchestrator "the epic's decision '<line>' is in question: <evidence>. Hold what rests on it and run compose reflect with this evidence."`.
**When compose itself fails** (the CLI crashes, behaves wrongly, or lacks what the project needs), the two jobs split:
- The team lead unblocks its own project with a teammate's workaround, never edits the compose repo, and reports `compose report ... tool-bug "<symptom, evidence, workaround used>"`. Every teammate's brief says the same.
- The engineering manager owns the tool. A tool-bug report from any teammate wakes its `watch` and lands in `~/.compose/tool-bugs.jsonl` with the CLI's commit and repo path (`cli_repo`). It briefs a toolsmith with two commands: `compose toolsmith --project <slug> | compose crew start --project <slug> --role toolsmith --work-repo <cli_repo> --brief -`, never `--cwd <cli_repo>`. The first prints the brief from the project's newest tool-bug entry (SKILL.md is the only skill file it names); with no entry it says so and exits non-zero.
- The toolsmith files the bug through `compose tool-bug file --project <slug> --body <file>`, which scrubs the text, searches open issues on prodoxx/compose, posts or comments, and records the issue URL in `tool-bugs.jsonl` as `issue`. gh must be logged in to post (`compose doctor` warns when it is not).
- A `--cwd` in a git repo always gets its own worktree on a new branch under that repo's `.claude/worktrees/` (the brief names it), the project's own repo included and whatever the role, so no existing checkout ever switches branches; only a test writer runs in the slot `testcrews` leased for it. `--work-repo` makes the same worktree but starts the session in the project worktree and hands it the worktree with `--add-dir`, so a repo Claude Code never trusted (the CLI's own checkout, often `~/.compose/src`) never parks the session at the trust prompt. If Claude Code has never trusted a `--cwd` repo, `crew start` stops and says so: use `--work-repo` for it, or ask the product owner to run `claude` there once and accept the prompt; never accept it for them.
- On a non-maintainer's machine the toolsmith never edits or commits. It reproduces, diagnoses, and reports `needs-user` with the saved draft and its path; the engineering manager shows the product owner the text, and on the go the toolsmith runs the same command with `--approved`, then reports `done` with the issue URL.
- On the maintainer's machine the toolsmith files first, fixes the root cause with a test on its own branch, runs the full suite, commits with no `Fixes #n`, comments the branch and the fix's commit on the issue, never merges or pushes, and reports `done` with the branch.
- The maintainer's fix still waits for the product owner: the engineering manager asks one line, "toolsmith fixed <X> on branch <B>, tests pass, merge?". On yes it fast-forwards the compose repo's main to the branch, closes the issue with `gh issue close <n> --comment "<what shipped>"`, returns the toolsmith's slot to the pool (`treehouse --root . return --force <path>`, or `git worktree remove` for a plain worktree), then tells each active team lead: "compose updated; re-read SKILL.md in full now".
The team lead reports at every point the product owner should hear about: `needs-user` carrying that one line, not the cards, and for a task list that departs from the settled spec (3b), any question it must ask itself, and a payment halt; `working` when a run starts and when it ends; `done` when the stack is verified, with the stack, cost, and decision needed.
The team lead drafts its Decisions and Plan text first and saves them in few `compose linear update --section` writes, one per section, with task detail on the task issues.
The team lead watches its own teammates: plain `compose watch` wakes on every task, run, verify, and teammate event except its own reports.
Every teammate session is started with `compose crew start --role <role> --title "<tab label>" --brief -`: its own tab in the project's space, a Claude session named `<slug>-<role>`, briefed with how to report. `compose crew list` shows each with its model and last report. One whose tab closed while its last report said working shows `ended`, and no stall or watch line counts it as working.
The model comes from `models.crew` in `~/.compose/config.json`: the role's entry, else `default`.
Planning runs on the strongest frontier model: the product owner and the engineering manager plan through the `wayfinder` teammate, which falls back to the `planner` entry when it has no entry of its own. The team lead delegates and never plans on `planner`: it uses its own `orchestrator` entry, else `default`. `planner` is a model plus an ordered `fallback` list (the user's config says which, for example GPT-6 Astra in pi, then Opus 5.5 at high effort): `crew start` probes each in turn (cached for the day) and takes the first that answers, printing which one it chose and why. A plan's mistakes cost every layer after it, so this is where the strongest model pays most. Groundwork and test-writing teammates get Opus: the tests are the implementers' spec, and in a benchmark Opus wrote the tightest suites (every seeded bug caught) and wrote them faster than Sonnet at high effort; a weak test becomes a shipped bug. A mechanical teammate (a revert, a stack or port fix, a one-command job) is started with `--model small`, Haiku, since speed is all it needs.
Nothing is closed by hand: a teammate session's tab closes by itself when the turn that reported `done` ends, so a teammate reports `done` only when nothing is left for it (work waiting on your review is `working`).
The team lead's own `done` runs `compose teardown`, which closes the implementers tab, the verify tab, and every teammate tab whose last report is `done`; `shell`, `status`, and the team lead stay, and teammates not yet done are left open and named.
Teardown also stops every server still listening from inside the project worktree (a teammate's dev server, a run's leftover) and stops the servers left listening in `.compose/<slug>/scratch/`, where teammates keep scratch copies; the files stay, because Linear comments cite them as evidence, and a teammate's `done` stops its servers the same way. `clean --delete-unmerged` removes an unmerged project entirely: its worktree folder, ignored files included, and its branch.
`compose crew stop --role <role>` remains for closing one early; it refuses a session that has not reported `done`, and `--force` is for the product owner's say-so only.
The harness's in-process subagent tool (Claude's `Agent`) has no pane, so herdr cannot show it: inside herdr it is not used.
Names match `[a-z][a-z0-9_-]{0,31}` and are unique among live agents.
Bare `compose` on a terminal opens the herdr session `compose`, so herdr is where compose runs by default.
A session that is outside herdr anyway (for example `COMPOSE_NO_HERDR=1`, or no terminal) has no engineering manager: the session the product owner started is the team lead, the CLI commands run headless, wayfinder questions are asked in the same batches in this session, and helpers are the harness's own subagents.
Each helper is started with a named model (`model: "sonnet"` for searches and fixes, `model: "haiku"` for a mechanical job), never the session's own by inheritance: a helper that only reads and edits pays the session's price on every turn.
