### 0b. Shape first, always
The architect (a solutions architect: it scopes the feature with the product owner and frames the product and technical choices, each with a recommendation) reads SKILL.md and sections/0b.md; nothing else of the skill is loaded.
The architect runs on every project, never skipped, even when a README, ticket, or spec seems to settle everything: a spec still leaves choices open (data model, scoring, toolchain, UX), and a choice made silently is one the product owner never saw.
Questions are asked once, as one card set, not as Linear tickets: text by default, relayed by the team lead to the engineering manager, which names every open card to the product owner in one message and points them at the project's page, `compose decisions`; the answers are recorded with `compose decide`, their words attached, as the map's Decisions so far.
It stays fast because the card set is only as big as the fog: a settled spec yields a short set, and the product owner accepts every recommendation with one word.
**The map** is the feature issue (or the epic, when there is one); its description is the map body: Destination, Notes, Decisions so far, Not yet specified, Out of scope.
It is the one decision record: no decision tickets, no per-question agents.
**The architect teammate.** Right after the groundwork teammate starts (0g), start one `architect` teammate; it runs on the planner model (the first of the configured chain that answers):
`compose architect --project <slug> --extra - <<'EOF' | compose crew start --project <slug> --role architect --title architect --brief -`
Add only the feature issue, the product owner's words, and the spec or README to read; the template carries the steps:
1. Read the map, its Linear lookups (below), the spec, and the repo; chart the map body on the feature issue.
Before any card, write two or three approaches to the feature under the map's Notes (`### Approaches`): a line each with what it changes and what it costs, and the one recommended with why; the cards then ask only what the approaches leave open, so a product owner who takes the recommendation answers a short set.
2. Write every open question as a card: the question, why it matters, the options with a line each and what each affects, and the recommended option marked
Every card is written to the map first, numbered under the feature's `## Not yet specified`, before anything is asked
The card format is `Q1. <question>` / `Why: <why it matters>` / `A. <option> - affects: <what choosing it changes>` (then B, C and D the same: two options at least, four at most) / `Recommendation: <letter> - <why>`; `compose report` refuses a card short of any of these.
Decide the channel per card with one test: are the options pictures, or words?
Words are text (the default): requirements, conceptual choices, tradeoffs, scope, toolchain; "where do the tokens live?" is text although tokens are UI.
Pictures are visual: a Frame0 wireframe, a layout or flow comparison, a diagram, side-by-side designs; "which of these three onboarding layouts?" is visual.
A visual card is never asked as text, and a text card never goes on the page.
Visual cards are on the map like every card, and go as well on the architect's one Lavish page at `.compose/<slug>/lavish/architect.html` (ignored with the rest of `.compose/`, never committed).
3. one ask: report `needs-user "<issue>: <n> cards <ids>; recommendation <one line>"` and, when visual cards exist, "visual cards open in Lavish: <url>"
<url> is the `url:` that `lavish-axi <file>` printed, copied and never retyped, in no second host form
`compose report` refuses a visual page without that link, a link that does not answer, cards already asked and not answered (one `reminder: ` line is allowed for a closed window), and a card that is not on the map in the card format, and it adds that the product owner may answer in text
Cards already in Decisions so far are never asked, and every open card of the project goes in this one ask
The team lead forwards the line unchanged to the engineering manager, which reads the issue once and gives the product owner one line per open card across the epic, in one message, with the page to open, `compose decisions --project <slug>`, never every card pasted in full (0h)
The engineering manager records the answers with `compose decide --project <slug> --quote "<their words>" "<card id>: <answer>"`, which moves each card to Decisions so far and wakes the team lead; the team lead tells the architect by card id with `herdr agent prompt <slug>-architect "decided: <card ids>"`, and outside herdr it asks and answers in this session (0h).
4. The visual page, only with visual cards: build it with Lavish's `input` playbook (`npx -y lavish-axi playbook input`) and its design rules (`npx -y lavish-axi design`: the project's own design system if it has one, else the Lavish-recommended Tailwind and DaisyUI CDN), `data-lavish-annotate="off"` on `<html>`, each card a form with `data-lavish-question`, the recommended option preselected, a free-text box, one answer control per card and one "accept every recommendation" control at the top.
Each sends exactly one `window.lavish.queuePrompt` with `text: "<question>: <answer>"` and `data: {question, answer}`; accept-all sends `data: {question: "accept-all", answer: [{question, answer}, ...]}` with every card's recommendation.
Open it with `npx -y lavish-axi <file>`, report `needs-user` as in step 3 before any poll (whatever the CLI's `next_step` text says), then wait with `npx -y lavish-axi poll <file> --owner architect --takeover` in the foreground of its own pane, never in the background and never `end` or `--reopen` on a session the product owner ended (Lavish's rules).
Answers arrive in the poll's `text` column (and as JSON after `Context data:` inside `prompt`), not as a `data` field.
Poll in rounds of 180000 ms (the Bash call's timeout) and run it again at once when a round ends with nothing: a forwarded text answer cannot reach a teammate blocked in a poll, and a killed poll loses no queued answer.
Acknowledge answers as they arrive with `npx -y lavish-axi reply <file> --agent-reply "<card ids> received"`, so the product owner sees they landed.
If the poll returns `browser_disconnected`, the session lives: run `npx -y lavish-axi <file>` once for its `url:`, report one `needs-user "reminder: ..."` with it, and poll again.
5. The architect never writes a Decisions so far line: `compose decide` moves each answered card from Not yet specified to one line there, `<card id>: <answer> (product owner, <date>; said: "<their words>")`, run by the engineering manager with the product owner's words attached, and wakes the team lead.
An answer that starts `away:` or `yolo:` is the engineering manager's recommendation, not the product owner's: the line ends `(away recommendation, unconfirmed, <date>)` or `(yolo recommendation, unconfirmed, <date>)`, the one its prefix names, until they confirm it (0h).
The planner says so on any story or task cut on one.
The same command with a quote confirms an unconfirmed line later, and `compose decide --change <cid>` records a change-of-course card, tagging the line with the change and striking through the line it supersedes.
When the team lead says a decision landed, the architect reads the map once (`compose linear get <id> --body`) and goes on from it; an answer that reaches it any other way goes back to the team lead, never onto the map by its hand.
6. Questions the answers open, and groundwork's toolchain findings as they arrive (0g; which version, which option), are asked the same way
New asks go out as the same one-line `needs-user "<issue>: <n> cards <ids>; recommendation <one line>"`; the team lead forwards it unchanged, and the answers come back by card id
The planner cuts what the product owner settles into implementer tasks; visual cards are added to the same page, then `npx -y lavish-axi poll <file> --agent-reply "<what changed>"` and wait again.
The builder check comes before done: the architect reads the map once as the planner will, with no one to ask; a how it leaves non-obvious (which component, which table, which flow) is one more card, asked as in 6, never a note for the planner to guess at.
7. When every card is answered and Not yet specified is empty, the feature is shaped: `npx -y lavish-axi end <file>` if a page was opened, report `done` with the decisions, and the team lead continues to step 1.
Every card carries a recommendation, never an answer chosen for the product owner: the grilling is HITL.
A **research** question is teammate work before the page asks it: a helper reads and reports, and the card states what it found.
A **prototype** question about how a screen or flow should look is drawn in Frame0 through the `frame0` MCP server (low-fi wireframes, one Frame0 page per question), exported with `export_page_as_image`, and shown on its card as an image: that card is visual and goes on the Lavish page.
Frame0 is off by default: a prototype question asks the team lead for a session started with `compose crew start --frame0` (the architect restarted that way, or a helper), and only that session has the `frame0` tools.
Each project draws in its own Frame0 app on `.compose/<slug>/design.f0`, never a shared one: run `compose frame0 up --project <slug>` before the first drawing and `compose frame0 save --project <slug>` after each batch; a later session that runs `up` edits the same file.
Only a session started with `crew start --frame0` has the `frame0` tools, pointed at that app; draw from such a session, never from an older one.
The first tool call makes Frame0 ask the product owner to allow "Frame0 MCP Server": report `needs-user` saying so and retry once they click Allow; if the tools still fail to connect, say so and wait.
Draw each page with one `compose frame0 draw --project <slug> --file <ops.json>`: a JSON list of the `frame0` tools' calls, `{"tool": "create_text", "as": "title", ...its arguments}`, where `"$title"` in a later id argument is that shape's id.
It prints one line per shape with its id and box and saves the file, so a page costs one turn, not one per shape; a single `frame0` tool call is for one fix.
Export a page once drawn, and again only after it changed.
`compose frame0 pages|move|delete` list and tidy its pages; never `curl` Frame0's API.
`teardown` saves and quits the project's Frame0.
Logic or stub prototypes go in code on a throwaway branch.
A **file** a skill would write (grilling notes, research findings, a decision log) is a **Linear document** in the repo's project instead (`compose linear doc create --title "<map>: <purpose>" --file <path>`, linked from the map's Notes), never a file in the repo.
The Lavish page is the one exception, kept under `.compose/`, which is never committed.
Before any question goes on the page, look for its answer in Linear first:
1. the map's Decisions so far and Notes, and the description and comments of the feature, its epic, and the story at hand
2. a `compose linear list --search "<terms>"` search, scoped to the project in `.compose/linear.json`, for the question's key terms, since another epic or feature may have decided it
A decision found there is settled: state it with its issue's name and link, build on it, never ask again.
Ask only when Linear is silent, or when two recorded decisions conflict; then put both on the card and ask which one stands.
"We need to make decisions" from the user is fog, whatever deliverables the same request lists: a PRD, epics, user flows, or a tech doc asked for up front are what the map and its decisions become after the grilling, not drafts written around decisions you picked.
When the product owner cannot answer now (a harness note says so, or no reply comes): keep any page open and its poll running, report `needs-user` with the card set (and the file), and stop there; 0r resumes it.
**An epic** gets one page for its open decisions (the epic is the map); once its features can be named, each feature's project runs its own architect page as above.
